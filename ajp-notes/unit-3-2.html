Unit 3.2: Remote Method Invocation (RMI)

How a Java program calls a method on an object running in a different JVM, possibly on another machine.

1Remote Method Invocation (RMI)

Definition

RMI (Remote Method Invocation) is a mechanism that lets an object in one JVM access or invoke methods of an object running in another JVM.

Description

  • It is used to build distributed applications, and it provides remote communication between Java programs.
  • It is provided in the java.rmi package.
  • A remote object is an object whose methods can be invoked from another JVM.

2Architecture of an RMI Application

An RMI application has two programs:

  • Server program: creates a remote object and makes its reference available to clients through the registry.
  • Client program: requests the remote object from the server and invokes its methods.
CLIENT JVM SERVER JVM ┌───────────────────┐ ┌───────────────────┐ │ Client Program │ │ Remote Object │ │ │ │ │ ▲ │ │ Stub │ │ Skeleton │ │ │ │ │ ▲ │ │ Remote Reference │ │ Remote Reference │ │ Layer (RRL) │ │ Layer (RRL) │ │ │ │ │ ▲ │ │ Transport Layer ─┼──── network ──┼─▶ Transport Layer │ └───────────────────┘ └───────────────────┘

Components

ComponentRole
Transport LayerConnects the client and server. It manages existing connections and sets up new ones.
StubA representation (proxy) of the remote object on the client. It acts as the gateway for the client program.
SkeletonAn object on the server side. The stub talks to the skeleton, which passes the request to the remote object.
RRL (Remote Reference Layer)Manages the references the client makes to the remote object.

3Working of an RMI Application

  1. The client calls a method on the remote object. The call is received by the stub, which passes it to the RRL.
  2. The client-side RRL calls invoke() on the remoteRef object and passes the request to the server-side RRL.
  3. The server-side RRL passes the request to the skeleton (the server proxy), which calls the actual method on the remote object.
  4. The result is passed all the way back to the client.
Client → Stub → RRL → Transport → RRL → Skeleton → Remote Object Client ← Stub ← RRL ← Transport ← RRL ← Skeleton ← (result)

4Marshalling and Unmarshalling

Marshalling (client side)Unmarshalling (server side)
When the client calls a remote method with parameters, the parameters are bundled into a message before being sent over the network.On the server, the packed parameters are unbundled and the required method is called.
Primitive parameters are put together and a header is attached.The values are extracted again.
Object parameters are serialized.Objects are deserialized.

The same thing happens in reverse for the return value: the server marshals it and the client unmarshals it.

5Stub and Skeleton

RMI uses stub and skeleton objects to communicate with the remote object.

Stub (client side)

The stub is the gateway for the client. All outgoing requests go through it, and it represents the remote object. When the caller invokes a method on the stub, the stub:

  1. Initiates a connection with the remote JVM.
  2. Writes and transmits (marshals) the parameters to the remote JVM.
  3. Waits for the result.
  4. Reads (unmarshals) the return value or exception.
  5. Returns the value to the caller.

Skeleton (server side)

The skeleton is the gateway for the server-side object. All incoming requests go through it. When it receives a request, it:

  1. Reads the parameters for the remote method.
  2. Invokes the method on the actual remote object.
  3. Writes and transmits (marshals) the result to the caller.
From the Java 2 SDK onwards, a new stub protocol removed the need for skeletons.

6Requirements for Distributed Applications

An application that does all of the following is a distributed application:

  • It locates the remote method.
  • It communicates with the remote objects.
  • It loads the class definitions for the objects.

RMI applications have all of these features, so they are distributed applications.

7RMI Registry

Definition

The RMI registry is a namespace where all server objects are placed.

  • When the server creates a remote object, it registers it with the registry using bind() or rebind() under a unique name called the bind name.
  • To call the remote object, the client needs a reference to it. The client fetches it from the registry by its bind name using lookup().
Server ──bind("sonoo", obj)──▶ [ RMI Registry ] Client ──lookup("sonoo")─────▶ [ RMI Registry ] ──stub──▶ Client Client ──stub.add(34,4)─────────────────────────────────▶ Server

8Goals of RMI

  • Minimise the complexity of the application.
  • Preserve type safety.
  • Distributed garbage collection.
  • Minimise the difference between working with local and remote objects.

9Naming Class

Definition

The java.rmi.Naming class provides methods to store and get remote objects in the RMI registry. All 5 methods are static.

Methods

MethodDescription
static Remote lookup(String name)Returns the reference (stub) of the remote object.
static void bind(String name, Remote obj)Binds the remote object to the given name. Throws AlreadyBoundException if the name is taken.
static void unbind(String name)Removes the remote object bound to the given name.
static void rebind(String name, Remote obj)Binds the remote object to the name, replacing any existing binding.
static String[] list(String name)Returns the names of all remote objects bound in the registry.

Names are written as URLs: rmi://host:port/bindName, e.g. rmi://localhost:5000/sonoo.

10RMI Example: 6 Steps

  1. Create the remote interface.
  2. Provide the implementation of the remote interface.
  3. Compile the implementation class and create the stub and skeleton using the rmic tool.
  4. Start the registry service with the rmiregistry tool.
  5. Create and start the server application.
  6. Create and start the client application.

The client needs only two files: the remote interface and the client program.

Step 1: Remote interface

Extend the Remote interface, and declare RemoteException on every method.

import java.rmi.*;

public interface Adder extends Remote {
    public int add(int x, int y) throws RemoteException;
}

Step 2: Implementation

Either extend UnicastRemoteObject or use its exportObject() method. If you extend it, you must define a constructor that declares RemoteException.

import java.rmi.*;
import java.rmi.server.*;

public class AdderRemote extends UnicastRemoteObject implements Adder {
    AdderRemote() throws RemoteException {
        super();
    }
    public int add(int x, int y) {
        return x + y;
    }
}

Step 3: Create the stub and skeleton

rmic AdderRemote
rmic was removed in Java 15. On modern Java, stubs are generated automatically at runtime, so you can skip this step.

Step 4: Start the registry

If no port is given, the default port 1099 is used. This example uses port 5000.

rmiregistry 5000

Step 5: Server, which binds the object as "sonoo"

import java.rmi.*;

public class MyServer {
    public static void main(String[] args) {
        try {
            Adder stub = new AdderRemote();
            Naming.rebind("rmi://localhost:5000/sonoo", stub);
        } catch (Exception e) {
            System.out.println(e);
        }
    }
}

Step 6: Client, which looks up the stub and calls add()

import java.rmi.*;

public class MyClient {
    public static void main(String[] args) {
        try {
            Adder stub = (Adder) Naming.lookup("rmi://localhost:5000/sonoo");
            System.out.println(stub.add(34, 4));     // prints 38
        } catch (Exception e) {
            System.out.println(e);
        }
    }
}

To call from another machine, replace localhost with the server's host name or IP address.

Running it (separate command prompts)

javac *.java          // 1. compile all files
rmic AdderRemote      // 2. stub + skeleton (old Java only)
rmiregistry 5000      // 3. prompt 1: start registry
java MyServer         // 4. prompt 2: start server
java MyClient         // 5. prompt 3: run client  → 38
