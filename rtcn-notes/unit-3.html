Unit 3: Transport Layer and SCTP

End-to-end delivery between applications: ports and sockets, TCP and UDP in detail, and SCTP with its streams, multihoming and chunks.

1The Transport Layer

The transport layer provides logical, end-to-end communication between application processes running on different hosts. It delivers data from one application to another reliably, in order and efficiently.

Position

OSI model TCP/IP model 7 Application ┐ 6 Presentation ├────▶ Application 5 Session ┘ 4 TRANSPORT ─────▶ TRANSPORT 3 Network ─────▶ Internet 2 Data link ┐ 1 Physical ┴────▶ Network access
  • In OSI it is Layer 4, above the network layer and below the session layer.
  • In TCP/IP it sits between the Internet layer and the Application layer.
  • It hides the complexity of routing and gives applications end-to-end delivery.

Main responsibilities

  • Reliable data transfer: data arrives correctly and without loss.
  • Flow control: the sender doesn't overwhelm the receiver.
  • Process-to-process delivery using port numbers, plus error control and congestion control.

2Basic Terms and Concepts

Segment and datagram

  • A segment is the unit of data in TCP: data plus a header with ports, sequence numbers and control flags.
  • A datagram is the unit of data in UDP.

End-to-end communication

  • Communication happens directly between the transport layers of sender and receiver.
  • The network layer does hop-to-hop delivery. The transport layer does end-to-end delivery, including error recovery and flow control.
Host A ──────── Router ───── Router ──── Host B │◀───────── transport: end-to-end ─────────▶│ │◀── network hop ──▶│◀── hop ──▶│◀── hop ──▶│

3Multiplexing and Demultiplexing

Multiplexing (at the sender) combines data from many applications into one stream, tagging each segment with its port number. Demultiplexing (at the receiver) reads the port number of each incoming segment and delivers it to the correct application.
SENDER RECEIVER Browser (port 50001) ┐ ┌─▶ Web server (port 80) Email (port 50002) ├─ MUX ─▶ network ─▶ DEMUX ─┼─▶ Mail server (port 25) DNS (port 50003) ┘ └─▶ DNS server (port 53)

4Ports and Sockets

Port

A port is a 16-bit number (0 – 65535) that TCP or UDP uses to identify a particular application process on a host.
RangeNameUse
0 – 1023Well-known portsReserved for common services: HTTP 80, HTTPS 443, FTP 21, SSH 22, SMTP 25, DNS 53
1024 – 49151Registered portsLess common applications that need a fixed port. Organisations can register them with IANA.
49152 – 65535Dynamic / ephemeral / privateTemporary, short-lived connections (e.g. the client side). Not assigned to anyone.

Socket

A socket is a communication endpoint, identified by the combination of IP address + transport protocol + port number.
  • Web server: (192.168.1.10, TCP, 80)
  • Email on the same host: (192.168.1.10, TCP, 25)
  • Same machine, different ports, so each application gets its own data.
Remember: IP address finds the host. Port finds the process. IP + port is the socket.

5Services Provided by the Transport Layer

ServiceDescription

6Transmission Control Protocol (TCP)

TCP is the most widely used transport protocol. It gives reliable, connection-oriented, byte-stream communication. Data arrives in order, without duplicates and free of errors.

Key features

  • Connection-oriented: a connection is set up with a three-way handshake.
  • Reliable: acknowledgements and retransmissions.
  • Flow control with sliding windows.
  • Congestion control to avoid overloading the network.
  • Byte-oriented: treats data as a stream of bytes, numbering every byte.
  • Full-duplex: data flows both ways at once.

Advantages

  • Reliable, ordered delivery
  • Flow and congestion control adapt to the network
  • Widely supported and well tested

Limitations

  • Higher overhead (connection management, error control)
  • Not suitable for low-latency or real-time traffic

Applications: web (HTTP/HTTPS), email (SMTP), file transfer (FTP), remote login (SSH).

7TCP Segment Header

A TCP segment is a header (20 to 60 bytes) plus data. The header carries the ports, sequence and acknowledgement numbers, and control flags.

8TCP Three-Way Handshake (Connection Establishment)

The three-way handshake sets up a TCP connection before any data is sent. Both sides synchronise their initial sequence numbers (ISNs) and agree to communicate.
Client (192.168.1.2) Server (192.168.1.10:80) │ ── SYN, Seq = 1000 ──────────────────────▶ │ 1 │ ◀── SYN-ACK, Seq = 5000, Ack = 1001 ────── │ 2 │ ── ACK, Seq = 1001, Ack = 5001 ──────────▶ │ 3 │ connection established │
  1. SYN: the client sends a segment with SYN set and its ISN (x = 1000).
  2. SYN-ACK: the server replies with SYN and ACK set. Ack = x + 1 = 1001, and it sends its own ISN (y = 5000).
  3. ACK: the client acknowledges with Ack = y + 1 = 5001. The connection is open.
Remember: SYN → SYN-ACK → ACK. The ack number is always "the other side's sequence number + 1".

9TCP Connection Termination (Four-Way Handshake)

TCP closes a connection with a four-step handshake, so that each side closes independently after finishing its own data and nothing is lost.
Host A (client) Host B (server) │ ── FIN, Seq = 2001 ─────────────────▶ │ 1 A done sending │ ◀── ACK, Ack = 2002 ───────────────── │ 2 half-closed: B may still send │ ◀── FIN, Seq = 3001 ───────────────── │ 3 B done sending │ ── ACK, Ack = 3002 ─────────────────▶ │ 4 fully closed (TIME-WAIT)
  1. FIN from sender (active close): Host A has finished sending but can still receive.
  2. ACK from receiver: Host B acknowledges. The connection is now half-open, and B can still send.
  3. FIN from receiver (passive close): B finishes and sends its own FIN.
  4. ACK from sender: A acknowledges, and both sides close.

The sockets pass through states such as FIN-WAIT-1, FIN-WAIT-2 and TIME-WAIT to close cleanly.

10TCP Flow Control, Congestion Control, Reliability & Timers

Flow control: sliding window

The receiver advertises a window size: how many bytes the sender may send without waiting for an ACK. This prevents receiver buffer overflow.

Bytes: [ sent & ACKed | sent, not ACKed | can send now | cannot send yet ] └──────── window (advertised by receiver) ───────┘ As ACKs arrive, the window slides to the right →

Congestion control

MechanismWhat it does
Slow startStarts with a small congestion window (cwnd) and grows it exponentially until a threshold.
Congestion avoidanceAfter the threshold, grows cwnd linearly to probe for bandwidth.
Fast retransmitResends a lost segment as soon as duplicate ACKs show it's missing, without waiting for the timer.
Fast recoveryAfter a loss, reduces cwnd instead of resetting it to one segment.

Reliable data transfer

Every byte is numbered and must be acknowledged. Lost or corrupted segments are resent, based on timers and duplicate ACKs.

TCP timers

  • Retransmission timer: resends a segment if its ACK doesn't arrive in time.
  • Delayed ACK timer: holds an ACK briefly so it can piggyback on outgoing data.
  • Persistence timer (handles zero-window deadlock) and keepalive timer (detects idle, dead connections).not in slides

11User Datagram Protocol (UDP)

UDP is a connectionless, lightweight, message-oriented transport protocol. It provides minimal service, with no reliability, ordering or flow control, so it's faster than TCP.

Header (8 bytes)

┌───────────────────┬─────────────────────────┐ │ Source port (16) │ Destination port (16) │ ├───────────────────┼─────────────────────────┤ │ Length (16) │ Checksum (16) │ └───────────────────┴─────────────────────────┘
  • Source / destination port: identify the applications.
  • Length: header + data.
  • Checksum: optional error check of header and data.

Characteristics

  • No connection setup. No delivery, order or integrity guarantee beyond the checksum.
  • No retransmission and no congestion control.
  • Preserves message boundaries: each datagram is independent.

When UDP is preferred

Live audio and video streaming · online multiplayer games · DNS queries · VoIP, wherever speed matters more than perfect delivery.

Advantages

  • Low overhead, minimal delay
  • Simple
  • Good for time-sensitive applications

Limitations

  • No guarantee of delivery or order
  • No congestion or flow control, so packets can be lost

13Other Transport Layer Protocols

ProtocolDescription

14Stream Control Transmission Protocol (SCTP)

SCTP is a general-purpose transport protocol designed for multimedia and stream traffic. It is a reliable, message-oriented protocol that combines the best features of UDP and TCP.

Comparing UDP, TCP and SCTP

  • UDP is message-oriented: it keeps message boundaries and each message is independent. But it's unreliable (messages can be lost, duplicated or out of order) and has no congestion or flow control.
  • TCP is byte-oriented: it stores messages as a stream of bytes and sends segments, so message boundaries are lost. But it's reliable (it detects duplicates, resends lost segments and delivers in order), with congestion and flow control.
  • SCTP gets the best of both: it preserves message boundaries like UDP and is reliable like TCP. It detects lost, duplicate and out-of-order data, and has congestion and flow control.
Remember: SCTP = UDP's message boundaries + TCP's reliability, plus multistreaming and multihoming.

15SCTP Services

1. Process-to-process communication

SCTP uses all the well-known ports in the TCP space.

2. Multiple streams (multistreaming)

SCTP allows several streams in each connection. In SCTP, a connection is called an association. If one stream is blocked, the other streams can still deliver their data.
Sending process Receiving process │ ▲ ┌──┴──┐ ── Stream 0 of data chunks ──────────────▶ ┌──┴──┐ │SCTP │ ── Stream 1 of data chunks ──────────────▶ │SCTP │ │ │ ── Stream n of data chunks ──────────────▶ │ │ └─────┘ (one association) └─────┘

This avoids TCP's head-of-line blocking, where one lost segment holds up everything behind it. For example, a web page's text, images and video can each have their own stream.

3. Multihoming

A multihomed host is connected to more than one physical network, with multiple IP addresses. An SCTP association allows multiple IP addresses at each end.
IP1 ──┐ ┌── IP3 Client ├──── Internet ────────┤ Server IP2 ──┘ └── IP4
  • Only one IP address per end is used at a time (the primary path). The others are kept as backups.
  • If the primary path fails, SCTP switches to another without breaking the association. This gives fault tolerance.

4. Full-duplex communication

Data flows in both directions at the same time. Each SCTP end has a sending buffer and a receiving buffer.

5. Connection-oriented service

SCTP is connection-oriented, but the connection is called an association. When process A wants to talk to process B:

  1. The two SCTPs establish an association.
  2. Data is exchanged in both directions.
  3. The association is terminated.

6. Reliable service

SCTP uses an acknowledgement mechanism to check that data arrived safely.

16SCTP Features

FeatureDescription
Transmission Sequence Number (TSN)The unit of data is a data chunk, and data chunks are numbered with a TSN. It does the same job as TCP's sequence number. 32 bits, randomly initialised between 0 and 232 − 1. Every data chunk carries its TSN.
Stream Identifier (SI)Identifies which stream a chunk belongs to in the association. 16 bits, starting at 0. Every data chunk carries it so the receiver can put it in the right stream.
Stream Sequence Number (SSN)Identifies the order of a chunk within its stream, so chunks are delivered to the right stream in the right order. 16 bits.
PacketsData goes in data chunks and control information in control chunks. Several of each can be packed into one packet. An SCTP packet plays the role of a TCP segment.
Acknowledgment numberTCP ACKs are byte-oriented (they refer to sequence numbers). SCTP ACKs are chunk-oriented (they refer to the TSN).
Flow controlLike TCP, it avoids overwhelming the receiver.
Error controlLike TCP, it uses TSNs and acknowledgement numbers for reliability.
Congestion controlLike TCP, it decides how many data chunks can be put into the network.

Example: TSN, SI and SSN in a flow of packets

First packet Second packet Third packet Fourth packet TSN 101 SI 0 SSN 0 TSN 104 SI 0 SSN 3 TSN 107 SI 1 SSN 2 TSN 110 SI 2 SSN 2 TSN 102 SI 0 SSN 1 TSN 105 SI 1 SSN 0 TSN 108 SI 2 SSN 0 TSN 111 SI 2 SSN 3 TSN 103 SI 0 SSN 2 TSN 106 SI 1 SSN 1 TSN 109 SI 2 SSN 1 ───────────────────────── flow from sender to receiver ─────────────────────────▶
  • TSN is a cumulative number across the whole association (101, 102, 103 …).
  • SI says which stream (0, 1, 2).
  • SSN is the chunk's position within its own stream (each stream counts from 0).
Remember: TSN identifies a chunk in the association, SI identifies the stream, and SSN identifies the chunk within the stream.

17SCTP Packet vs TCP Segment

A segment in TCP A packet in SCTP ┌───────────────┬──────────────────┐ ┌───────────────┬──────────────────┐ │ Source port │ Destination port │ │ Source port │ Destination port │ ├───────────────┴──────────────────┤ ├───────────────┴──────────────────┤ │ Sequence number │ │ Verification tag │ │ Acknowledgment number │ │ Checksum │ │ HL │ Control flags │ Window size │ ├──────────────────────────────────┤ │ Checksum │ Urgent pointer │ │ Control chunks │ │ Options │ ├──────────────────────────────────┤ ├──────────────────────────────────┤ │ Data chunks │ │ Data bytes │ │ │ └──────────────────────────────────┘ └──────────────────────────────────┘

Differences

  1. TCP keeps control information in the header. SCTP keeps it in control chunks.
  2. A TCP segment's data is one entity. An SCTP packet can carry several data chunks, each possibly from a different stream.
  3. TCP has an options section. SCTP has none, and handles options by defining new chunk types.
  4. TCP's mandatory header is 20 bytes. SCTP's general header is only 12 bytes, because:
    • the TSN belongs to each data chunk, so it's in the chunk header;
    • the acknowledgement number and window size are in control chunks;
    • no header length field is needed, since there are no options and the length is fixed at 12 bytes;
    • no urgent pointer is needed.
  5. TCP's checksum is 16 bits. SCTP's is 32 bits (CRC-32).
  6. SCTP's verification tag identifies the association. TCP has no equivalent: in TCP the IPs and ports define a connection, but with multihoming SCTP needs a separate tag.
  7. TCP has one sequence number for the first data byte. An SCTP packet has several data chunks, each with its own TSN, SI and SSN.
  8. TCP control segments (SYN, FIN) use up a sequence number. SCTP control chunks never use a TSN, SI or SSN, which belong only to data chunks.

18SCTP Packet Format & General Header

An SCTP packet has a mandatory 12-byte general header followed by a set of chunks. Control chunks maintain the association and data chunks carry user data. Control chunks always come before data chunks.
┌──────────────────────────────┐ │ General header (12 bytes) │ ├──────────────────────────────┤ │ Chunk 1 (variable length) │ ├──────────────────────────────┤ │ ... │ ├──────────────────────────────┤ │ Chunk N (variable length) │ └──────────────────────────────┘

General header

It identifies the association the packet belongs to, makes sure the packet really belongs to that association, and protects the integrity of the whole packet.

┌──────────────────────────┬──────────────────────────┐ │ Source port (16) │ Destination port (16) │ ├──────────────────────────┴──────────────────────────┤ │ Verification tag (32) │ ├─────────────────────────────────────────────────────┤ │ Checksum (32) │ └─────────────────────────────────────────────────────┘
FieldDescription
Source port (16)Sending port.
Destination port (16)Receiving port.
Verification tag (32)Matches the packet to its association, so a packet from an old association can't be mistaken for a current one. It's repeated in every packet, with a separate tag for each direction.
Checksum (32)A CRC-32 checksum.

19Chunks

A chunk is a block that carries either control information or user data. All chunks share a common layout: Type, Flag, Length, then the chunk information.
0 7 8 15 16 31 ┌────────────┬────────────┬─────────────────────────┐ │ Type (8) │ Flag (8) │ Length (16) │ ├────────────┴────────────┴─────────────────────────┤ │ Chunk information (multiple of 4 bytes) │ └───────────────────────────────────────────────────┘
FieldDescription
Type (8 bits)Up to 256 chunk types. Only a few are defined, and the rest are reserved.
Flag (8 bits)Special flags. Each bit's meaning depends on the chunk type.
Length (16 bits)Total chunk size in bytes, including type, flag and length, but excluding padding. An empty chunk has length 4.

Padding rule

The information section must be a multiple of 4 bytes. If it isn't, padding bytes (eight 0s each) are added at the end. Padding isn't counted in the length.

  • Length = 17: the next multiple of 4 is 20, so there are 3 bytes of padding to discard.
  • Length = 16: already a multiple of 4, so there's no padding.

20DATA Chunk

The DATA chunk (type 0) carries the user data. A packet can carry zero or more DATA chunks.
0 7 8 13 14 15 16 31 ┌────────────┬──────────┬─┬─┬─┬───────────────────────┐ │ Type: 0 │ Reserved │U│B│E│ Length │ ├────────────┴──────────┴─┴─┴─┴───────────────────────┤ │ Transmission sequence number (TSN) │ ├──────────────────────────┬──────────────────────────┤ │ Stream identifier (SI) │ Stream sequence no. (SSN)│ ├──────────────────────────┴──────────────────────────┤ │ Protocol identifier │ ├─────────────────────────────────────────────────────┤ │ User data │ └─────────────────────────────────────────────────────┘

Flag bits (5 reserved + 3 defined)

  • U (Unordered): when 1, the data is unordered and the SSN is ignored.
  • B (Beginning) and E (End): together they give a chunk's position in a fragmented message:
BEMeaning
11Not fragmented: the whole message is in this one chunk (first and last)
10First fragment
01Last fragment
00Middle fragment

Fields

FieldDescription
TSN (32)Transmission sequence number.
Stream identifier (16)Which stream. All chunks of one stream in one direction carry the same SI.
Stream sequence number (16)The chunk's number within its stream, in one direction.
Protocol identifier (32)Lets the application say what type of data it is.
User dataThe actual data.

User data rules

  1. A chunk can't carry data from more than one message, but one message can be split over several chunks.
  2. The field can't be empty: at least 1 byte. So the length is never less than 17 (16-byte chunk header + 1 byte of data).
  3. If the data doesn't end on a 32-bit boundary, padding is added. It isn't counted in the length.

Establishment: four-way handshake
