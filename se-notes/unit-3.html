Unit 3: Design Engineering

Turning the SRS into a design: the core design concepts, cohesion and coupling, the design model and architectural styles.

1Design Engineering

The design phase of the SDLC produces a solution to the problem described in the SRS. Its output is the Software Design Document (SDD).
SRS (what to build) ──▶ DESIGN ──▶ SDD (how to build it) ──▶ Coding

Two levels of design

Conceptual DesignTechnical Design
Written in simple, customer-understandable language.Written for developers.
Explains system characteristics and describes functionality.Covers hardware components, the hierarchy of software components, software and network architecture.
Independent of implementation.Data structures and data flow, I/O components, interfaces.
Linked to the requirement document.Linked to implementation.

2Design Process

Software design is the process of transforming user requirements into a suitable form that helps the programmer code and implement the software. It turns the SRS document into the design document.

What gets designed and documented

  • The different modules required.
  • Control relationships among modules.
  • Interfaces among modules.
  • Data structures of the modules.
  • Algorithms needed to implement each module.

Software design is both a process (a sequence of steps that describe all aspects of the software) and a model (which gives different views of the software).

3Objectives of Software Design

ObjectiveMeaning
CorrectnessCorrectly implements all the required functionality.
EfficiencyOptimises resources, time and cost.
UnderstandabilityEasy to understand: modular, with modules arranged in layers.
CompletenessHas all the components: data structures, modules, external interfaces.
MaintainabilityEasy to change when the customer asks for changes.
Mnemonic: CEUCM, "Can Every User Change Me?": Correctness, Efficiency, Understandability, Completeness, Maintainability.

4Design Concepts

Design concepts are the fundamental principles that guide the designer towards a good-quality design.
ConceptOne-line idea
AbstractionShow the essentials and hide the details.
ModularityDivide the software into separate modules.
Information hidingA module's internals are hidden from other modules.
RefinementAdd detail step by step, top-down.
Functional independenceEach module does one job: high cohesion, low coupling.

5Abstraction

Abstraction means focusing on the essential features of a problem or solution while hiding the low-level details.

Levels of abstraction

  • Highest level: the solution is stated in broad terms, in the language of the problem.
  • Lower levels: a more procedural, detailed description.
  • Lowest level: the solution is stated so that it can be implemented directly as code.

Types of abstraction

TypeMeaningExample
Procedural abstractionA named sequence of instructions with a specific, limited function"Open" a door means walk to the door, grasp the knob, turn it, pull, and step away.
Data abstractionA named collection of data that describes a data object"Door" has type, swing direction, opening mechanism, weight and dimensions.
Control abstractionA program control mechanism without its internal detailsA semaphore used to synchronise activities in an OS.

6Modularity

Modularity means dividing software into separately named and addressable components called modules, which are integrated to meet the problem's requirements. "Modularity is the single attribute of software that allows a program to be intellectually manageable."
  • Monolithic software (one large module) is almost impossible to understand. It has too many control paths and variables, and too much overall complexity.
  • Splitting the problem into modules makes each piece easier to solve (divide and conquer).

Modularity and software cost

Cost │ \ / total cost │ \ cost per module / │ \___ ______/ │ \____ ____/ cost to integrate │ \/ ← region of minimum cost (M) └──────────────────────────── Number of modules
  • More modules means a lower cost per module, because each is smaller.
  • But more modules also means a higher integration (interface) cost.
  • So there is an optimum number of modules (M) where the total cost is lowest. Avoid both under-modularity and over-modularity.

7Information Hiding

Information hiding means modules are designed so that the information inside a module (its algorithms and data) is not accessible to other modules that don't need it.
  • Modules communicate only through well-defined interfaces.
  • Benefits: changes inside one module don't affect others, errors don't spread, and testing and maintenance are easier.
  • In OOP this is achieved with encapsulation (private members).
┌─── Module A ───┐ ┌─── Module B ───┐ │ hidden data │ interface │ hidden data │ │ hidden logic │ ◀────only────▶ │ hidden logic │ └────────────────┘ └────────────────┘

8Refinement (Stepwise Refinement)

Refinement is a top-down design approach and a process of elaboration. A high-level statement of a function is decomposed step by step until programming-language statements are reached.
  • The original statement describes a function or information, but not how it works internally.
  • Each refinement step adds more detail.
  • Every step involves design decisions, so the designer should be aware of the criteria and of alternative solutions.
  • Abstraction and refinement are complementary: abstraction hides low-level details, and refinement reveals them step by step.

Example

Open door └─ Walk to door └─ Grasp knob └─ Reach out hand └─ Close fingers around knob └─ Turn knob and pull └─ Rotate knob 90° └─ Pull door towards you └─ Step away

9Functional Independence

Functional independence is achieved by building modules that have a single-minded function and avoid excessive interaction with other modules. A functionally independent module has high cohesion and low coupling.
  • It follows directly from modularity, abstraction and information hiding.
  • It is essential for good design: such modules are easier to develop, test and maintain, and errors spread less.

Two measures

Cohesion (keep HIGH)Coupling (keep LOW)
How strongly the elements inside a module work together for one purposeHow much a module depends on other modules
An intra-module measureAn inter-module measure
Best: functional cohesionBest: no coupling or data coupling
Golden rule: High Cohesion + Low Coupling = Good Design.

10Phases (Levels) of Design

The design phase turns the customer requirements in the SRS into a form that can be implemented in a programming language. It has three levels:

LevelDescription
1. Interface designThe highest level. Treats the system as a black box and focuses on its interaction with users, devices and other systems.
2. Architectural designBreaks the system into major components, with their responsibilities, properties, interfaces and interactions.
3. Detailed designThe internal design of each component: data structures and algorithms.

11Design Model

The design model represents the features of the software that help engineers build it: the data structure, program architecture, interfaces and component-level detail. It gives different views of the system, like the architect's plan for a house.

Methods such as data-driven, pattern-driven or object-oriented design all follow a set of design principles. The model has four elements, usually drawn as a pyramid:

╱╲ ╱ ╲ Component-level design ╱────╲ ╱ ╲ Interface design ╱────────╲ ╱ ╲ Architectural design ╱────────────╲ ╱ ╲ Data design ╱────────────────╲
ElementDescription
Data designRepresents the data objects and their relationships in an ER diagram, and the structure of the data as tables. It covers 1:1, 1:N and M:N relationships.
Architectural designDefines the relationships between the major structural elements and breaks the system into interacting components. It is shown as a block diagram.
Interface designHow the software communicates with users (the system's behaviour), through controls and displays. It is optimised through usability testing.
Component-level designTurns the architecture's structural elements into a procedural description of each component. Components don't need to handle central concerns such as backup and security of data.

12Software Architecture

Software architecture is the hierarchical structure of program components, the way they interact, and the structure of the data they use.

Set of properties

PropertyMeaning
Structural propertiesThe components (modules, objects, filters) and how they are packaged and interact.
Extra-functional propertiesHow the architecture achieves performance, capacity, reliability, security, adaptability and so on.
Families of related systemsReusable patterns that recur in the design of similar systems.

Architectural design models

ModelRepresents
StructuralAn organised collection of program components
FrameworkRepeatable architectural frameworks (patterns) in similar applications
DynamicThe behavioural aspects of the architecture
ProcessThe design of the business or technical process
FunctionalThe functional hierarchy of the system

13Control Architecture (Program Structure Terms)

The control hierarchy (program structure) shows how modules are organised and call each other. It is usually drawn as a tree.
M ← depth level 1 ┌───────┼───────┐ a b c ← level 2 ┌─┴─┐ │ ┌─┴─┐ d e f g h ← level 3 │ │ └──┬──┘ i ← level 4 (fan-in of i = 2) width = 5 (max modules at one level) · depth = 4 · fan-out of M = 3
TermMeaning
Superordinate moduleA module that controls another (e.g. M over a, b, c).
Subordinate moduleA module controlled by another (e.g. a, b, c under M).
DepthThe number of levels of control.
WidthThe overall span of control: the most modules at any one level.
Fan-outThe number of modules directly controlled by a module.
Fan-inThe number of modules that directly control a module. High fan-in means good reuse.
VisibilityThe set of components that can be invoked or used by a given component.
ConnectivityThe set of components that a given component actually invokes or uses.
Good design: high fan-in for low-level utility modules, moderate fan-out (avoid very high fan-out).

14Structural Partitioning

Partitioning is breaking a large, complex system into smaller, more manageable and often independent components. The program structure can be partitioned horizontally or vertically.

Horizontal partitioning

Separate branches of the hierarchy for each major program function, usually three: input, processing (transformation) and output.

Main control ┌──────────────┼──────────────┐ Input Processing Output (branch) (branch) (branch)
  • Benefits: easier to test and maintain, fewer side effects, easier to extend.
  • Drawback: more data is passed across module interfaces, which can complicate control flow.

Vertical partitioning (factoring)

Control (decision-making) modules sit at the top, and the workers that do the actual processing sit at the bottom.

Decision-making (control) modules ← top │ Intermediate modules │ Worker modules (input, compute, output) ← bottom
  • Benefit: changes in worker modules (the most frequent kind of change) are less likely to spread upward, so the structure is easier to maintain.

15Cohesion

Cohesion is a measure of how strongly the elements within a module are related. A cohesive module performs a single task and needs little interaction with other parts of the program. Ideally, it does just one thing. Cohesion is a natural extension of information hiding.

The cohesion spectrum (worst to best)

LOW (bad) ◀──────────────────────────────────────────────────▶ HIGH (good) Coincidental → Logical → Temporal → Procedural → Communicational → Sequential → Functional
TypeMeaningExample
1. Coincidental (worst)Tasks are only loosely related, or not related at all.A "utilities" module that prints, sorts and sends email
2. LogicalTasks are logically similar (same category), and one is chosen by a flag.One module for all input: keyboard, file or network
3. TemporalTasks must run in the same span of time.Initialisation: open files, set counters, clear the screen
4. ProceduralElements are related and must run in a specific order.Check the password, then open the menu
5. CommunicationalAll elements work on the same data (one area of a data structure).Calculate the average and the maximum of the same marks list
6. SequentialThe output of one part is the input to the next, like an assembly line.Read data → validate → format
7. Functional (best)All parts contribute to one well-defined task.A calculateTax() module
Mnemonic (worst to best): "Can Lazy Teachers Pass Clever Students Fairly?": Coincidental, Logical, Temporal, Procedural, Communicational, Sequential, Functional.

16Coupling

Coupling is a measure of the interdependence between modules. It depends on how complex the interfaces between them are. We aim for the lowest possible coupling.
  • Simple connections make software easier to understand and less prone to the "ripple effect", where an error in one place spreads through the system.

Types of coupling (best to worst)

LOW (good) ◀────────────────────────────────────────────────▶ HIGH (bad) No → Data → Stamp → Control → External → Common → Content
TypeMeaningExample
No coupling (best)Modules don't communicate at all.Two completely independent modules
Data couplingModules share data through simple parameters.area(length, width)
Stamp couplingA whole data structure is passed, but only part of it is used.Passing a whole Student record just to use the roll number
Control couplingOne module controls the flow of another by passing a flag that says what to do.print(data, mode), where the mode flag decides the behaviour
External couplingModules share an externally imposed data format, protocol or device interface.Two modules using the same file format or hardware device
Common couplingModules share the same global data.Several modules reading and writing a global variable
Content coupling (worst)One module modifies or relies on the internal workings of another.Jumping into the middle of another module, or changing its local data
Mnemonic (best to worst): "No Dog Should Chase Every Cat Constantly": No, Data, Stamp, Control, External, Common, Content.

CohesionCoupling
Relationship within a moduleRelationship between modules
Should be highShould be low
Measures a module's functional strengthMeasures a module's independence
Best: functional · Worst: coincidentalBest: no or data coupling · Worst: content

17Architectural Styles

An architectural style is a template for building a system category. Architectural design represents the structure of data and program components, their properties, and the relationships among them.

Each style describes

  • A set of components (e.g. a database or computational modules).
  • A set of connectors that let the components communicate, coordinate and cooperate.
  • Constraints on how components can be integrated into a system.
  • Semantic models that let a designer understand the overall system properties from the known properties of its parts.

Taxonomy (types)

  1. Data-centered architecture
  2. Data flow architecture
  3. Call and return architecture
  4. Object-oriented architecture
  5. Layered architecture

18Data-Centered Architecture

A data store (a file or database) sits at the centre and is accessed frequently by other components, which add, update, delete or modify the data.
Client A Client B ╲ ╱ ▼ ▼ ┌──────────────┐ │ Central │ ◀── Client C │ Data Store │ │ (repository) │ ◀── Client D └──────────────┘
  • Client software accesses a central repository. It can be passive, with clients accessing data independently.
  • A variant is the "blackboard", which notifies clients when data they're interested in changes.
  • It promotes integrability: you can change existing components or add new ones without affecting the other clients, because clients work independently.
  • Examples: library management systems, banking databases.

19Data Flow Architecture

Used when input data is transformed through a series of computational components into output data.

Pipe and filter

Input ──pipe──▶ [Filter 1] ──pipe──▶ [Filter 2] ──pipe──▶ [Filter 3] ──▶ Output
  • Filters are components connected by pipes, which carry data from one filter to the next.
  • Each filter works independently of the filters before and after it. It expects input in a set form and produces output in a set form.

Batch sequential

If the data flow becomes a single line of transforms, it is called batch sequential.

[Validate] ──▶ [Sort] ──▶ [Update] ──▶ [Report]
  • Examples: compilers (lexer → parser → code generator), Unix pipes (cat | grep | sort).

20Call and Return Architecture

This style gives a program structure that is relatively easy to modify and scale.

Sub-styles

  • Main program / subprogram: the classic structure. Function is decomposed into a control hierarchy, where the main program invokes components, which may in turn invoke others.
  • Remote procedure call (RPC): the components of a main/subprogram architecture are distributed across multiple computers on a network.
Main Program ┌─────────┼─────────┐ Controller 1 Controller 2 Controller 3 ┌──┴──┐ │ ┌──┴──┐ App 1 App 2 App 3 App 4 App 5

21Object-Oriented Architecture

The system's components encapsulate data and the operations that manipulate that data. Components communicate and coordinate through message passing.
┌─── Object A ───┐ message ┌─── Object B ───┐ │ data │ ───────────▶ │ data │ │ operations() │ ◀─────────── │ operations() │ └────────────────┘ reply └────────────────┘ │ │ └─────── message ──▶ Object C ◀─┘
  • Supports encapsulation, inheritance and polymorphism.
  • Good for reuse and maintainability.

22Layered Architecture

A number of layers are defined, each doing operations that get progressively closer to the machine instruction set.
┌──────────────────────────────┐ │ User Interface layer │ ← outer layer ├──────────────────────────────┤ │ Application layer │ ├──────────────────────────────┤ │ Utility layer │ ├──────────────────────────────┤ │ Core layer (OS interface) │ ← inner layer └──────────────────────────────┘
  • Outer layer: components handle user interface operations.
  • Inner layer: components handle operating system interfacing.
  • Intermediate layers: provide utility services and application functions.
  • Each layer uses only the services of the layer directly below it.
  • Examples: the OSI network model, OS architecture.
