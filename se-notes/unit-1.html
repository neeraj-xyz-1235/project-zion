Unit 1: Introduction to Software Engineering

What software engineering is, how software has evolved, the myths around it, and the process models used to build it.

1What is Software Engineering?

The two words

  • Software is made of three things:
    • programs that provide function and performance
    • data structures that let the programs handle information
    • documents that describe how the programs work and how to use them
  • Engineering is a discipline that applies scientific and technical methods to design and produce a product.

Definition (IEEE)

Software engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software; that is, the application of engineering to software.

Definition (general)

Software engineering is the process of analysing user requirements and then designing, building and testing a software application that satisfies those requirements.
Remember: Software = Programs + Data structures + Documents. The IEEE definition has three keywords: systematic, disciplined and quantifiable.

2Need & Objectives of Software Engineering

Why is software engineering required?

  • Large software: big systems and organisations can't be managed without a systematic approach.
  • Scalability: software must be able to grow.
  • Dynamic nature: requirements keep changing, and SE keeps those changes under control.
  • Performance: supports better management of performance.
  • Cost and quality: produces cost-effective, better-quality products.

Objectives

  • Improve the quality of software products.
  • Increase customer satisfaction.
  • Increase productivity.

3The Evolving Role of Software

Software has passed through four eras since the 1950s:

EraPeriodKey features
1st Era1950s – mid 1960sBatch-oriented · limited distribution · custom software. Job mobility was low, and design and documentation were often non-existent.
2nd Eramid 1960s – 1970sMulti-user · real-time · database · product software. Multiprogramming and interactive systems appeared, and DBMSs were introduced. All of this led to the need for software maintenance.
3rd Eramid 1970s – 1980sDistributed systems · embedded intelligence · low-cost software · consumer impact. Local and global networks, high-bandwidth digital communication and embedded systems.
4th Era1990s – 2000sPowerful desktops · OOP technology · expert systems · neural networks · parallel computing. AI, fuzzy logic, virtual reality and multimedia.

4Software Characteristics

Software is a logical rather than physical system element, so it behaves differently from hardware.

Characteristics

  1. Software is developed or engineered. It is not manufactured in the classical sense. Its cost is in engineering, not in production.
  2. Most software is custom-built rather than assembled from existing components.
  3. Software doesn't "wear out", but it does deteriorate due to change.

Failure curves

HARDWARE ("bathtub curve") SOFTWARE (idealised vs actual) Failure Failure rate │\ / rate │\ ▲ change ▲ change │ \ infant / wear │ \ /\ /\ actual │ \ mortality / out │ \_/ \_______/ \__ ... │ \_____________/ │ ____________________ idealised └──────────────────── Time └──────────────────────── Time
  • Hardware fails often at first (infant mortality), then stays steady, then fails more as parts wear out (dust, heat, vibration).
  • Software isn't affected by those physical factors. Ideally its failure rate flattens out, but every change introduces new errors, which causes spikes. Over time the minimum failure rate creeps up. This is deterioration due to change.

6Generic View of Software Engineering

Whatever the project, software engineering work falls into three generic phases: Definition (what?), Development (how?) and Maintenance (change).

1. Definition phase: focuses on WHAT

  • What information is to be processed, what function and performance are wanted, what the system should do, which interfaces are needed, what design constraints exist, and what the validation criteria are.
  • Three steps: System/Information Engineering → Software Project Planning → Requirement Analysis.

2. Development phase: focuses on HOW

  • How data is structured, how functions and procedures are implemented, how the design becomes code, and how testing is done.
  • Steps: Design → Code generation → Testing.

3. Maintenance phase: focuses on CHANGE

TypePurpose
CorrectionFix defects found after delivery.
AdaptationAdapt to changes in the environment (new OS, hardware, rules).
EnhancementAdd new functionality.
PreventionChange the code so it's easier to correct, adapt and enhance later (also called re-engineering).

7The Software Process

A software process is the set of activities used to design and build a software product.

Four fundamental activities (common to all processes)

  1. Software specification: define what the software should do and the constraints on it.
  2. Software design and implementation: produce software that meets the specification.
  3. Software validation: check that the software does what the customer needs.
  4. Software evolution: change the software as customer needs change.

8Software Myths

Software myths are false beliefs or misleading attitudes about software and how it's built. They cause serious problems for managers, customers and developers.

Three types

(i) Management myths

MythFact
We already have a book of standards and procedures, so that's enough.Standards are often incomplete, outdated or unused. Each new project brings new problems.
Buying the latest hardware will improve development.CASE tools and good practices matter more than hardware for quality and productivity.
If we fall behind schedule, we can add more programmers.Adding people to a late project makes it later (Brooks' law). Existing staff lose time training the newcomers.

(ii) Customer myths

MythFact
A general statement of objectives is enough to start coding. Details can come later.Unclear requirements lead to failure. Clear requirements come only from continuous communication between customer and developer.
Requirements change, but software is flexible, so changes are easy.Changes are cheap early on but very costly later, once design and code exist.

(iii) Practitioner (developer) myths

MythFact
Once the program is written and works, the job is done.60–80% of all effort is spent after first delivery, on maintenance.
You can't assess quality until the program is running.Technical reviews are an effective quality filter, and they work earlier than testing.
The working program is the only deliverable.Documentation, manuals and guides are also needed for support.
Software engineering means lots of needless documents and slows us down.SE is about quality, not paperwork. Better quality means less rework, which means faster delivery.

9Process Models & SDLC

A process model (or software engineering paradigm) is a development strategy made of process, methods and tools, chosen to suit the project.

Which model to pick depends on the nature of the project and application, the methods and tools to be used, and the controls and deliverables required.

SDLC (Software Development Life Cycle)

SDLC is the process the software industry uses to design, develop and test high-quality software that meets customer expectations within time and cost estimates. It is also called the Software Development Process.

SDLC is a framework that defines the tasks done at each step of development.

Planning → Requirement Analysis → Design → Coding → Testing → Deployment → Maintenance

Families of models in this unit

10Waterfall Model

The Waterfall model is the first and simplest process model. It is a linear-sequential life cycle model: each phase must be fully completed before the next begins, and phases never overlap.

Phases

Requirement Gathering & Analysis └─▶ System Design └─▶ Implementation (units + unit testing) └─▶ Integration & Testing └─▶ Deployment └─▶ Maintenance
  1. Requirement gathering & analysis: capture all requirements and document them in the SRS.
  2. System design: study the SRS and prepare the design, including hardware, system requirements and the overall architecture.
  3. Implementation: build the system in small programs called units. Each unit is tested (unit testing).
  4. Integration & testing: combine the units into one system and test it for faults and failures.
  5. Deployment: release the product to the customer or the market.
  6. Maintenance: release patches for issues found, and better versions as enhancements.

Characteristics

  • Sequential, with no going back.
  • Each phase has specific deliverables and a review.
  • Heavily documented.

Advantages

  • Simple and easy to understand and use
  • Easy to manage, because the model is rigid
  • Phases are done one at a time
  • Good for small projects with clear requirements
  • Clearly defined stages and milestones
  • Process and results are well documented

Disadvantages

  • No working software until late in the cycle
  • High risk and uncertainty
  • Poor for complex, object-oriented or long projects
  • Can't accommodate changing requirements
  • Hard to measure progress within a stage
  • "Big-bang" integration at the end hides problems until late
When to use: requirements are clear, fixed and well understood, and the project is short.

11Incremental Model

In the Incremental model, requirements are divided into multiple standalone modules (increments). Each increment goes through requirements, design, implementation and testing, and each release adds functionality to the previous one until the complete system is built.
Increment 1: Req → Design → Code → Test → Release 1 (core features) Increment 2: Req → Design → Code → Test → Release 2 (+ more) Increment 3: Req → Design → Code → Test → Release 3 (+ more) ... until complete

Phases (per increment)

  1. Requirement analysis: identify the requirements and understand the functional needs.
  2. Design & development: design the functionality and decide the development method.
  3. Testing: test both the existing functions and the newly added ones.
  4. Implementation: do the final coding, then test. After each pass, the product is enhanced and moves closer to the final system.

Advantages

  • Errors are easy to recognise
  • Easier to test and debug
  • More flexible
  • Risk is easier to manage, since it's handled in each iteration
  • The client gets important functionality early

Disadvantages

  • Needs good planning
  • Total cost is high
  • Needs well-defined module interfaces

12RAD Model (Rapid Application Development)

The RAD model is based on prototyping and iterative development with no specific planning. Writing the software itself involves the planning. It aims for very short development cycles, often 60–90 days.

Characteristics

  • Gathers requirements through workshops or focus groups.
  • The customer tests the prototypes early, in iterations.
  • Reuses existing prototypes and components.
  • Continuous integration and rapid delivery.
  • Work is split across several teams working in parallel.

Phases

Business Modelling → Data Modelling → Process Modelling → Application Generation → Testing & Turnover
PhaseWhat happens
Business modellingModel the flow of information between business functions: what information drives the business, where it comes from, and how it's processed.
Data modellingRefine that information into data objects, with their attributes and relationships.
Process modellingTurn the data objects into the information flow. Describe processes for adding, deleting, retrieving and modifying data.
Application generationBuild the system using automated tools that turn the models into prototypes.
Testing & turnoverTesting time is reduced because prototypes are tested in each iteration. Interfaces and data flow still need full testing.

Advantages

  • Reduced development time
  • More reuse of components
  • Quick initial reviews
  • Encourages customer feedback
  • Integrating from the start avoids integration issues

Disadvantages

  • Depends on a strong team to identify requirements
  • Only works for systems that can be modularised
  • Needs highly skilled developers and designers
  • Highly dependent on modelling skills
  • Too costly for cheap projects (modelling and code generators are expensive)

13Evolutionary Process Models

Evolutionary process models are iterative models that produce more complete versions of the software with each iteration. They're designed for products whose requirements evolve over time.

Why they're needed

  • Business and product requirements often change during development, so a straight-line path to the final product isn't realistic.
  • Tight deadlines may force a limited first version, with the rest added later.

Types

  1. Prototyping
  2. Spiral model
  3. Concurrent development model

14Prototype Model

Software prototyping means building a prototype, a working model that shows the product's functionality but may not contain the real logic, so customer requirements can be understood early.

Flow

Requirement analysis → Quick design → Build prototype → Customer evaluation ▲ │ └──── Refine (not OK) ◀───┘ │ OK Final SRS → Design → Code → Test → Deliver

Steps

  1. Basic requirement identification: understand the basic requirements, especially the user interface. Internal details such as performance and security can wait.
  2. Develop the initial prototype: show the basic requirements and UI. Workarounds can be used to give the right look and feel.
  3. Review the prototype: show it to the customer and stakeholders, and collect feedback in an organised way.
  4. Revise and enhance: discuss the feedback and negotiate on time, budget and technical feasibility. Repeat until the customer is satisfied.

Types of prototype (dimensions)

  • Horizontal prototype: shows the whole user interface, with little logic behind it.
  • Vertical prototype: one function built in depth (for example a database connection).
  • Throwaway prototypes are discarded, while evolutionary ones grow into the final system.not in slides

Advantages

  • Users are involved before implementation
  • Users understand the system better through a working model
  • Defects are found early, which saves time and cost
  • Quicker feedback leads to better solutions
  • Missing and confusing functions are easy to spot

Disadvantages

  • Relying too much on the prototype can mean too little requirement analysis
  • Users may confuse the prototype with the real system
  • Scope may grow beyond the original plan
  • Developers may try to reuse an unsuitable prototype
  • Too much effort may go into prototypes if not monitored
When to use: the customer isn't sure about the requirements, or the UI is very important.

15Spiral Model

The Spiral model (by Barry Boehm) combines iterative development (prototyping) with the systematic, controlled aspects of the waterfall model, with a very high emphasis on risk analysis. Each loop of the spiral is one phase, and it allows incremental releases.

Four phases (quadrants), repeated every loop

Identification (requirements) │ Evaluation & ◀─────┼─────▶ Design Risk Analysis │ │ Construct / Build (each loop goes outward, cost and completeness increase)
PhaseWhat happens
IdentificationGather business requirements in the first loop. In later loops, identify system, subsystem and unit requirements.
DesignConceptual design first. Later loops do architectural, logical, physical and final design.
Construct / BuildProduce the software in each loop. In the first loop, build a POC (Proof of Concept) to get feedback.
Evaluation & risk analysisIdentify, estimate and monitor technical and management risks (schedule slippage, cost overrun). The customer evaluates the build and gives feedback.

Advantages

  • Accommodates changing requirements
  • Makes extensive use of prototypes
  • Captures requirements more accurately
  • Users see the system early
  • Risky parts are built first, which improves risk management

Disadvantages

  • More complex to manage
  • The end of the project may not be known early
  • Not suitable or too expensive for small, low-risk projects
  • The spiral may go on indefinitely
  • Many intermediate stages mean a lot of documentation
Remember: Spiral = Waterfall + Prototyping + Risk analysis. Use it for large, high-risk projects.

16Concurrent Development Model

In the Concurrent development model (also called the concurrent model), all activities exist at the same time, but each is in a different state. Events trigger transitions from one state to another.

States of an activity

None ──▶ Under development ──▶ Awaiting changes ▲ │ │ │ ▼ ▼ Under revision ◀──────── Under review │ ▼ Baselined ──▶ Done

Example

  • Early in the project, the communication activity finishes its first iteration and moves to awaiting changes.
  • The modeling activity, which was in the none state, moves to under development.
  • If the customer asks for changes to the requirements, modeling moves from under development to awaiting changes.

Advantages

  • Applies to all types of software development
  • Easy to understand and use
  • Gives immediate feedback from testing
  • Gives an accurate picture of the project's current state

Disadvantages

  • Needs better communication among team members
  • The status of every activity has to be tracked

17Specialized Process Models

Specialized process models take features from one or more conventional models. They're used when a narrowly defined software engineering approach is chosen.

Types

ModelIdea
Component-based developmentBuild the application from reusable pre-built components (see the next topic).
Formal methods modelnot in slidesSpecify, develop and verify software using mathematical notation. This removes ambiguity and is used for safety-critical systems such as aircraft and medical devices.
Aspect-oriented software development (AOSD)not in slidesSeparates cross-cutting concerns (security, logging, memory management) into "aspects" that affect many parts of the system.

18Component-Based Development (CBD) Model

The component-based development model composes applications from prepackaged, reusable software components (classes). Object-oriented technology provides the framework for it. It is evolutionary and iterative, much like the spiral model.

Working steps

  1. Identify the candidate components (classes) by examining the data and the algorithms.
  2. Check whether these components already exist in the library from previous projects.
  3. If they do, extract them from the library and use them.
  4. If not, build the component.
  5. Put the new component in the library. That completes one iteration.
  6. Repeat steps 1–5 for n iterations until the application is complete.
Identify candidate components │ ▼ Look up components in library ──found──▶ Extract & reuse ─┐ │ not found │ ▼ ▼ Build new component ──▶ Put in library ──▶ Construct n-th iteration of system

Advantages

  • Much less software to build, which cuts cost and risk
  • Faster delivery
  • More reliable, because components are already tested
  • Easier to manage complexity
  • Reduced development time

Disadvantages

  • Requirements may have to be compromised to fit the components
  • Less control over evolution, since component versions are controlled by others
  • Maintaining components can be an issue

19Personal Software Process (PSP)

The Personal Software Process (PSP) emphasises personal measurement of the work product an engineer produces and of its quality. Each engineer improves their own process.

Philosophy

  • A system is only as good as its worst component, and a component's quality depends on the individual who built it and the process they followed.
  • Engineers should measure, track and analyse their work, learn from variations in their performance, and apply the lessons.
  • PSP stresses finding errors early, and understanding the kinds of errors you tend to make.

Five framework activities

ActivityWhat happens
PlanningIsolate the requirements. Estimate size, resources and defects. Record the metrics, identify tasks and create a schedule.
High-level designWrite external specifications for each component and create the component design. Build prototypes where uncertain. Track all issues.
High-level design reviewApply formal verification to find errors in the design.
DevelopmentRefine and review the component design. Generate, review, compile and test the code.
PostmortemUse the collected metrics to judge how effective the process was, and improve it.
The slides spell it "Personnel Software Process". The correct name is Personal Software Process (by Watts Humphrey).

20Team Software Process (TSP)

The goal of the Team Software Process (TSP) is to build a "self-directed" project team that produces high-quality software. It extends PSP to teams.

Objectives

  • Build self-directed teams (3 to about 20 engineers) that plan and track their own work, set goals, and own their processes.
  • Show managers how to coach and motivate teams and keep performance at its peak.
  • Speed up software process improvement.
  • Give improvement guidance to high-maturity organisations.

A self-directed team

  • Defines roles and responsibilities for each member.
  • Tracks quantitative project data.
  • Picks a suitable process and a strategy for following it.
  • Defines local standards.
  • Continually assesses risk and reacts to it.
  • Tracks, manages and reports project status.

Framework activities

Project Launch → High-level Design → Implementation → Integration & Test → Postmortem

TSP uses scripts, forms and standards to guide members. Scripts define specific process activities.

Launch script

  1. Review objectives with management, then agree on and document the team's goals.
  2. Establish team roles.
  3. Define the team's development process.
  4. Make a quality plan and set quality targets.
  5. Plan the support facilities needed.

21Agile Process Model

Agile means swift or versatile. The Agile process model is an approach based on iterative development. Work is broken into small iterations, typically 1–4 weeks each, without long-term planning.

Characteristics

  • The scope and requirements are set at the start. The number, length and scope of iterations are planned in advance.
  • Each iteration runs a full mini-SDLC: planning, requirements, design, coding and testing. A working product is shown to the client at the end.
  • Small parts reduce project risk and overall delivery time.
  • Values customer collaboration, working software and responding to change.

Phases

Requirements gathering → Design requirements → Construction/Iteration → Testing → Deployment → Feedback ▲ │ └──────────────────────────── next iteration ◀──────────────────────────────────┘
  1. Requirements gathering: define requirements and business opportunities, estimate time and effort, and check technical and economic feasibility.
  2. Design the requirements: work with stakeholders, using user-flow or high-level UML diagrams.
  3. Construction / iteration: designers and developers build a working product, starting with minimal functionality.
  4. Testing: the QA team checks performance and looks for bugs.
  5. Deployment: release the product into the user's environment.
  6. Feedback: collect feedback on the product and work through it.

Types of agile models

Extreme Programming (XP) · Adaptive Software Development (ASD) · Dynamic Systems Development Method (DSDM) · Scrum · Crystal · Feature Driven Development (FDD) · Agile Modeling (AM)

Advantagesnot in slides

  • Frequent delivery of working software
  • Welcomes changing requirements
  • Close customer involvement
  • Lower risk thanks to short iterations

Disadvantagesnot in slides

  • Less documentation
  • Hard to estimate effort for large projects
  • Needs experienced, committed team members
  • Depends heavily on customer availability

22Extreme Programming (XP)

Extreme Programming (XP) is the most widely used agile process, originally proposed by Kent Beck. It has four framework activities: Planning, Design, Coding and Testing.
Planning (user stories, values) → Design (KIS, CRC cards, spike) → Coding (pair programming) → Testing (unit + acceptance) ▲ │ └──────────────────────────── software increment, project velocity ◀───────────────────────┘
ActivityPractices
XP PlanningStarts with user stories. The team assesses each story and assigns a cost. Stories are grouped into a deliverable increment, and a delivery date is committed. After the first increment, project velocity is used to set later delivery dates.
XP DesignFollows the KIS (Keep It Simple) principle. Uses CRC cards (Class-Responsibility-Collaborator). For hard problems, builds a spike solution (a design prototype). Encourages refactoring, an iterative improvement of the internal design.
XP CodingWrite the unit tests before coding. Use pair programming: two people at one computer.
XP TestingAll unit tests run daily. The customer defines acceptance tests to check the visible functionality.
Remember XP keywords: user stories, velocity, KIS, CRC cards, spike solution, refactoring, pair programming, test-first, acceptance tests.
